## Language Gaps

- **Names of a C header outside `core:` aren't known.** `c-reserved-headers.txt` lists what the headers of the `core:` library declare, so a program's names are renamed around those it includes. With `use "zlib.h"`, a global named like something in it can still break the C build. Fields of records aren't renamed at all, so a field named like a macro of an included header gets that macro's text.
- **Layout gaps:** no `align(n)` on a single field, no unnamed padding bit-fields (use a named field), no zero-width bit-fields, no flexible array members (`char data[]`), and no generic `union`.
- **A library's per-thread pool lives until the library is unloaded,** even after the thread ends, unless that thread calls `NAME_clear()` first. `export` works on functions only, not on globals.
- **`mut` doesn't reach function values or interfaces.** `fn move` as a value has the type `(@Point, Int) => None`, called with `addrof p`, and an interface's `fn bump()` isn't satisfied by `fn bump(mut c: Counter)`. A receiver is passed by address only when it is a variable, field, element or `@p`; `make().move()` needs `val`/`var` first.
- **A record's fields being fixed is only checked where eclang assigns them.** `addrof r.x` of a record that isn't a `mut rec` gives an `@Int` through which `r.x` can change, as `addrof` of a `val` already does, and a `declare fn` given an `@Point` (or a C struct holding one) may write it. It is shallow: a field's array or what a pointer field points to can still change. A record whose fields are fixed that extends a `mut rec` can have its inherited fields changed where it is used as the parent (`@Animal`). A generic function that changes a field of its `<T>` without saying `<mut T>` is rejected only in the copy for a fixed record, where the error points into its body rather than at the call.
- **`x.f()` with a `mut` receiver inside a loop is an error after a check of x made before the loop,** where `f(mut x)` makes the loop forget the check. The receiver's kind is only known while compiling, after the loop has relied on the check.
- **Closures have a few gaps.** Lambdas are one expression, so a longer body needs a function. A call's result can't be called directly (`adder(1)(2)`, `table[0](1)`): store it first. Function values have no `==`. A `var` checked before a lambda that uses it isn't narrowed inside it, as it is shared (a `val` is). A C function pointer becomes an eclang function value only by wrapping it in a lambda (`fn (x) = f(x)`).
- **Contracts are only on eclang functions.** A `declare fn` can't have `requires`, though C functions are where a stated precondition would help most: that needs a checking wrapper per binding. A `requires` is checked even when the caller already proved it (`if i < a.len do at(a, i)`), and an `ensures` can't compare with the value a parameter had on entry (no `old(x)`). An `ensures` proves nothing to the caller.
- **Assertion reports show whole operands.** `assert n % 2 == 0` shows `n % 2 = 1`, not `n`. Arguments of a call are shown only when the call is the whole condition. Panics other than `assert` and contracts (bounds, `x!`, division) still name only the line, not the function.
- **The hint after a `debug assert` is a guess.** Any later error about null or a union in the function mentions the `debug` check, also when it is about another value.
- **`debug` isn't highlighted everywhere it is a statement** (the TextMate grammar can't see the start of a statement), and `fits`/`outlives` are highlighted wherever a word between two names looks like them.
- **The other contextual words are highlighted by guesses too.** `where`, `requires` and `ensures` are highlighted when a space and something that could start a condition follow them, so a variable of that name before a value (`f(where (x))`) is too, and `it` and `here` are highlighted everywhere, also as names of variables.
- **`Volatile<T>` is only the type of a variable.** A volatile field (a memory-mapped register in a `declare struct`) or a pointer to volatile memory (`@Volatile<UInt>`) can't be written, as the type system has no qualifiers: such code needs a C helper. It also changes nothing for eclang: narrowing and constant folding treat the variable as any other `var`, though another thread or a signal handler may change it between two reads.
- **Running out of stack is only reported on the main thread,** on Linux on x86-64 and arm64, and has no line number. In a `thread.spawn` thread, or after `core:term.ec` has replaced the handler, it is a plain segfault, as there is no separate signal stack there. A `lib` has no check either: the stack belongs to the program using it.
- **A trailing `if` can't end a block before `else`.** `if a do` / `    x = 1 if b` / `else do` is a syntax error at the `if` of `x = 1 if b` (also when that line isn't first in the block). Write `if b do` / `    x = 1` instead.
- **`new ((Int, Int))[n]` doesn't parse as a type.** An array of tuples of named types takes `(Int, Int)` as a tuple expression ("'Int' is not defined"); it works when a type parameter is in the tuple (`new ((Size, <T>))[n]`, as in `core:array.ec`). `filled(n, (0, 0))` of `core:array.ec` is a way around it (`core:grid.ec` uses it).
- **A misleading error for `a ?? f() ?? b`.** With a call in the middle of a `??` chain, the compiler says "`try` can't be used on the right side of `??`" although there is no `try`: `p.values.get(name) ?? os.env(name) ?? ""`. Split it with `if val`.
- **eclang can't write `long long`, `signed char` or a C enum type.** `Long` is C's `long`, `Char` is `char` and an enum is an `Int`: the same size and representation on Linux on x86-64 and arm64, so values pass unchanged, but a pointer to one isn't a pointer to the other for gcc. So `bindings/sqlite` leaves out `sqlite3_update_hook` (its callback takes a `sqlite3_int64`) and takes `sqlite3_serialize`'s size as an `@Any?`, and `tools/check-bindings.py --fields` takes those pairs as the same type.

## Language Memory Safety

- **A loop's pool per round is only as safe as the lifetime checks.** The compiler gives a loop's rounds a pool (`LoopPools`) when those checks would accept a `pool do` around the body, so it has their gaps: a round's memory kept by a C function whose `declare fn` doesn't say so (`kept`, `escaping`), or hidden by an unchecked cast (`!as`) where a later read can't be followed, would be freed too early. `unsafe` code counts as keeping what it is given. `--check-memory` finds such a case at runtime. Only loops outside `pool do` blocks and lambdas get one, and a call counts as allocating when its function may (`thread.join`'s error, say), not only when it does, which costs a pool that frees nothing.
- **Lifetimes follow only what a function stores of its arguments.** A call is checked against what the callee keeps (`Escapes`). A C function keeps only what its `declare fn` marks `kept` or `escaping`; the bindings of `core:` mark those of APR's hash tables, tables, pool cleanups and user data, and `setvbuf`, but a binding written without them is taken at its word. A call of a function value is checked against every lambda and `fn name` of its type that keeps something in its arguments, so a call can be rejected for what another function of that type does. A lambda or `fn name` that keeps its parameters (or memory it allocates) anywhere but in its own arguments is rejected, even when every call would give it memory that lives long enough (`unsafe` says so). A store through what a call returned counts as a store into the arguments whose type can reach what the result points at; an `@Any` field (a C handle, a user's context) doesn't count, so a value stored behind one through an unchecked cast isn't followed. What a callee keeps is checked at the call, but doesn't change what the caller knows afterwards: `set(addrof o, addrof x)` with `fn set(pp: @@Int, v: @Int) do @pp = v`, then `ret o`, isn't rejected. A function's locals are followed by name for the whole body, so a name reused for something else can make a call look like it keeps more than it does. Freeing a pool the function didn't make needs `own p: Pool` or `unsafe`; with `unsafe destroy p` in `fn drop(p: Pool)`, the caller can still use what was in p after `drop(p)`: the compiler takes `unsafe` at its word. A pool given to an `own` parameter is gone for the caller even when the callee gives it back (in a record it returns, say): only one function owns a pool at a time, and ownership doesn't come back.
- **What a function's result points into is known by parameter, after a failed try, and not for every function.** `Escapes.resultRoots` says which parameters a result may point into, from the body (`ret`, `throw`, `try`, and what the function stores behind a pointer it returns). As bodies are compiled in any order, a call only uses it when the program is compiled again after failing on memory (`Compiler.compileHere`, up to 4 times), so a program that compiles the first time is checked as before: a call's result may point into every argument. A `ret` of a call's result after a deferred free (`defer destroy p`, `ret id(s)`) is checked once every body is compiled (`Alloc.via`). There is no summary, so every argument counts, for function values, C functions, calls with a `mut` argument, generic functions until an instance is compiled in the try before, and functions with an error, an `addrof` of a local, or a lambda that changes their `var`s. It is by parameter, not by field: a function that returns `m.input` counts as returning into `m` (`core:regex.ec`'s `matchOf` takes the input as a parameter of its own for that reason). A lambda's result has no summary either.
- **`const assert a outlives b` is conservative about pools the function made.** Memory of a `new Pool` only outlives memory in that same pool, even when the pool is plainly freed later (`defer destroy p` around a `pool do` block), since the compiler doesn't order a pool's `destroy` against a scope's end. `x in pool` outside a `pool do` block can only be shown for memory allocated in the current pool by this function (`new`, `${...}`, a call), not for what a parameter points into.
- **A pool's memory stored behind a pointer is only checked for a parameter written directly.** `o.s = format(p, ...)` then `destroy p` is an error, but not through a copy of the pointer (`val q = o`, then `q.s = ...`) or through a call (`set(o, format(p, ...))`). A callee can free the pool only with `unsafe`. A global only sees what the same function did to it.
- **Only `if` joins its branches without the path that skips them.** After `if ... else`, what is known about pools is what one of the branches knew. Other branching forms (`when`, `x ?? y`, an inline `if`, `try ... catch`) also count the way past them that runs none of their arms: an `s` freed before a `when` whose every arm gives s a new value is still rejected after it. Memory that a variable holds on every path where it wasn't freed is fine, as with `if`.
- **A variable's local memory is never forgotten.** `var p: @Int = addrof x`, `p = addrof g`, `ret p` is rejected, as `setOrigin` only adds to what p may point into. In a loop, all of a variable's assignments reach every use, unless it is defined in the loop.
- **Threads are only partly checked.** `thread.spawn`'s data is `escaping`: it can't be the spawning function's local memory or in a pool it made, but memory of its current pool belongs to its caller, which may free it (a `pool do` around the call) while the thread runs; that includes the `sync` records the data points to (a `thread.Queue` in the caller's pool). The data and what a lambda captures are `flat` (`Sharing`), but `sync rec` isn't checked: it vouches that its fields are only used under its lock, and a plain field of a `sync` record can still race. `unsafe thread.spawn(...)` (as `core:http.ec` does with its `Server`) and `thread.Channel`, which hands over `@Any` pointers, skip the check: a `Channel` item allocated in a thread's pool dangles when the thread ends, and so does a global set there. A `flat` function value that isn't a lambda written in the call is rejected, as what it captured can't be seen. A `Thread` is a `resource`, but any use of the variable counts, so one joined on only some paths isn't caught.
- **`--check-memory` only sees eclang's allocations.** Memory APR allocates itself (`apr_pstrdup`, `apr_psprintf`) stays in the pool's blocks, where a use after the pool is freed isn't reported, and C's `printf("%s")` of freed memory isn't checked by AddressSanitizer (`io.log` and `io.print` use `fwrite`, which is). The generated C `main` is reported at the line of the program's last statement.
- **Some memory-unsafe operations need no `unsafe` or `!as`.** `Mapped.text`, which `fs.unmap` leaves dangling. Reading a field of a `union` that holds no pointer (an Int read from a union holding a Float) isn't checked either, as its bits are still a valid number.
- **A non-null value can still be null.** `unsafe new (<T>)[n]` returned from a generic function before every element is written gives a `(@Int)[]` with NULLs; `unsafe` says the programmer has checked that. Globals that need each other through functions can't be ordered, so one reads the other before it is set (a warning, not an error: a table of handlers that reads itself only when called is fine). The `IRCNotNull` check covers a `declare fn`'s result and the pointer fields of C structs read with `.`, also when written through (`p.next.x = 1`), but not arguments of C callbacks.

## Library

- **A `SlotPool` key can match again after 2^31 reuses of its slot.** Each slot counts its uses in a `UInt`, which wraps around. A value taken away stays in its slot (and keeps what it points to alive) until the slot is used again or the pool is freed.
- **`core:term.ec` keeps at most 64 KB of stderr in full-screen mode.** More than that is written to the screen when the buffer fills.
- **`core:term.ec` only sees one code point per cell.** Combining marks are dropped from a `Screen`, and emoji sequences (flags, skin tones) are measured one code point at a time.
- **`apr_socket_recv` takes its buffer as a `CString`.** A `new Char[n]` buffer needs `buf.data !as CString`, and `cstr(s)` looks like the obvious way but received nothing into `s`. `core:net.ec` hides this.
- **`net.Poller` only knows readiness of the socket.** What a connection has read ahead (`net.buffered`) or TLS holds decrypted doesn't make it ready, so a loop must read that before waiting again, and a socket must be removed before it is closed (APR keeps a record of it otherwise). Its capacity is fixed when it is made. Adding and removing from other threads while one waits needs epoll (Linux).
- **`core:tls.ec` covers the usual client and server, not all of TLS.** No client certificates, ALPN (so no HTTP/2), session resumption, OCSP or certificate pinning, and the server has one certificate (no SNI choice between several). Its OpenSSL bindings are checked only where OpenSSL's headers are installed, and `c-reserved-headers.txt` lists the names of `openssl/*.h` only when `tools/gen-c-reserved.py` ran with them. A server's handshake that would have to wait to write (a full socket buffer, which a handshake hardly fills) waits until the dispatcher's next readable event or the timeout.
- **`core:json.ec` gives up on a lone surrogate (`"\ud83d"`).** It is an error, where some parsers put U+FFFD in its place.
- **Some `core:` bindings still take `@T`.** Those where C also accepts NULL (`strtol`'s `end`, `pthread_join`'s result, an optional output) need `addrof x`, as `out` takes no null, and so do `core:apr/portable.ec`, the atomic pointer swaps and inputs passed by pointer. The `priv` records of `core:` modules (parsers, regex machines) are still plain records used as `@Name`.
- **`bindings/ffmpeg` covers the usual API, not all of it.** Not bound yet: libavfilter, libavdevice, hardware decoding (`AVHWDeviceContext`), side data, subtitles (`AVSubtitle`), bitstream filters, custom I/O (`avio_alloc_context` with callbacks), `av_log_set_callback` (a C `va_list`) and most struct fields nobody reads. The structs list only the fields programs commonly use; more can be added from the headers, as C's layout comes from them. `AVChannelLayout.u` (a union holding the mask) isn't bound: use `av_channel_layout_describe` or compare layouts.
- **`bindings/sqlite` and `bindings/cimgui` leave parts out.** SQLite: the authorizer, virtual tables, VFSes, mutexes, the session extension and the UTF-16 functions; `SQLITE_STATIC`, on purpose (SQLite would keep a pointer into eclang memory unchecked). cimgui: `imgui_internal.h`, ImGui's own backends (`cimgui_impl.h`), `va_list` functions, the methods of templated types (`ImVector_*`), anonymous unions in structs (`ImGuiStoragePair`'s value) and fields starting with `_`. `tests/run.sh` compiles `bindings/cimgui/examples/raylib.ec` but doesn't run it, as it needs a display.
- **Two `core:` bindings don't match their C types exactly**, as `tools/check-bindings.py --fields` reports (so `tests/run.sh` doesn't run it on `core:`): `apr_descriptor` (`core:apr/poll.ec`) is a `declare struct` but a C union typedef, and the fields of `utsname` (`core:c/utsname.ec`) are `Char[]c` but `char[65]` in C. Both work, because eclang never names the C type or takes a field's address, but should become `declare union rec` and `Char[65]`.
- **`core:test.ec` can't find tests.** Tests are listed by hand with `test.run`: finding them needs a way to list the functions of a file.
- **A function with a `caller` parameter, as a value, takes it.** `fn check` as a `(Bool, Location) => None` works, but there is no function value that fills in the place of the call by itself. `here` and `caller` need `core:errors.ec`'s `Location` (or a String or Int parameter).
- **`core:regex.ec` has no Unicode tables.** `\p{L}` is an error, and `ignoreCase`, `\w`, `\d` and `\b` only know ASCII. A loop around something that can match nothing, as in `(\b|a)+`, may go round once more or less than in Perl or Python, as in Go and RE2.
- **`core:http.ec` holds everything in memory.** Bodies can't be streamed, in either direction. The client opens a connection for each request, and has no cookies or compression.
- **`core:parallel.ec` doesn't check what its function shares.** Its threads end before the call returns, so what they read can't be freed under them, which is why the function may capture Strings and arrays, unlike `thread.spawn`'s. But nothing stops it from changing a `var` it captures, or a record it can reach, from several threads at once without a lock: the compiler has no way to say "shared, but only read" for the length of a call. A `thread.WorkerPool` is allocated in the current pool and isn't a `resource`: one that is never stopped keeps its threads waiting, and freeing its pool under them crashes.
- **`SortedMap`'s `less` must be a strict order.** Two keys neither of which comes before the other are the same key, so a `less` such as `<=`, or one that isn't transitive, loses keys or finds the wrong one; nothing checks it. Its iterator looks for the key after the one before at each step (log2(n) steps each), which lets the map change during the loop but makes a full loop take n·log2(n) steps.
- **The server of `core:http.ec` hands a connection to a worker once a request's head has arrived.** Idle connections and slow heads hold no worker, but a body sent slowly does, for up to `timeout` between reads, and so does a head larger than the 8 KB the dispatcher buffers. A handler that takes long holds its worker too: there are `workers` of them.

## Editor

- **Completion only knows the types of code the compiler reaches.** The compiler compiles the file with a probe at the cursor (`Completion.kt`): in a generic function nobody calls yet, in a file whose declarations (or any `use`d file's) have errors, or when another line of the file doesn't parse, it finds nothing, and the extension offers names from declarations without types. A line being written is tried as it is, with its brackets closed, and as `val _ = <expression before the dot>` (losing the expected type). Atoms are those the expected type allows, then those the program used before the cursor in compile order. In a union copy of a function, the narrowed types are those of the first copy compiled. Each request compiles the whole program (as each check does), so a large program answers slowly.

## Standard library, newer modules

- **A variable named like a module hides it.** With `fn f(path: String)`, `path.join(...)` in its body is the parameter's, and the error says "It is defined in module 'path'; write `path.join`", which the code already does. It should say that the variable hides the module. `core:path.ec` is where this comes up most; `core:fs.ec` reaches it through private helpers for that reason.
- **`core:big.ec` has no operators.** `a.add(b)` instead of `a + b`, as eclang has no operator overloading. An Integer or Decimal holds an array, so `==` and `hash` don't work on them, and they can't be keys of a Map or Set (use their `text`). Multiplication is the schoolbook method, so numbers of hundreds of thousands of digits are slow.
- **Two `uuid.v7()` made in the same millisecond are in no particular order.** RFC 9562's counter methods aren't used.
- **`bench`'s `cpu` is the whole program's.** It counts every thread, also those that have nothing to do with the benchmark.
- **`x as Size` of an Int sometimes has no cast in the C.** `fn f(): Size = g() as Size` with an Int `g()` writes `return g();`, which is the same value in C but warns with `-Wconversion` (only `tools/check-bindings.py` uses that). `val n = g()` then `n as Size` writes the cast.
